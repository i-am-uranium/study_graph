# v0.2 Quality RAG — Implementation Plan

This plan turns the v0.2 goals in [ROADMAP.md](ROADMAP.md) into concrete, ordered work
grounded in the current codebase. Ordered by dependency and value: each phase is
shippable on its own.

## Current state (baseline)

- `app/services/retrieval.py` loads **every** chunk for the selected documents into
  Python and computes cosine similarity in a loop (`retrieve_chunks`). The pgvector
  index defined in `0001_initial_schema` is never used. This is the primary quality
  *and* scaling bottleneck.
- Single-stage retrieval, fixed `limit=8`, no reranking.
- `app/services/generation.py` sets `confidence_notes` to a hardcoded string; nothing
  verifies the answer is grounded in the cited chunks.
- No retrieval/generation eval fixtures.
- Observability is limited to `setup_logging`; no per-stage timing or provider-call
  metrics.
- No user-facing retry for failed ingestion beyond re-running the whole job; no retry
  for failed generation.

## Local OSS model stack (decided — IMPLEMENTED 2026-07-03)

The whole inference stack must be OSS and locally runnable. Decisions (2026-07-03):

| Role | Model | License | Serving | Dims / ctx |
| --- | --- | --- | --- | --- |
| Embeddings | **Qwen3-Embedding-0.6B** | Apache 2.0 | Ollama (`/v1/embeddings`) | 1024 / 32k |
| Reranker | **bge-reranker-v2-m3** | Apache 2.0 | Infinity sidecar (`michaelf34/infinity`, `/rerank`) | — / 512 |
| Chat | **Qwen3-8B** | Apache 2.0 | Ollama (`/v1/chat/completions`) | — / 32k |

**Status:** the OpenAI→Ollama migration and reranker wiring have landed. `providers.py`
talks to Ollama (optional key, `dimensions` gated by `SEND_EMBEDDING_DIMENSIONS`, Qwen3
`/no_think`), `retrieve_chunks` reranks the candidate pool via the Infinity sidecar with
vector-order fallback, `EMBEDDING_DIMENSIONS` is 1024, and `docker compose up` pre-pulls
the models via an `ollama-init` service. Backend (43) + frontend (30) tests green.
Still open from the phases below: pgvector-native retrieval (Phase 1 — still a Python
cosine scan), eval fixtures, coverage/verification, observability, retry controls.

Chat rationale: keeps the whole stack in one Apache-2.0 Qwen3 family (embedding + chat),
leads on instruction-following (needed for "answer only from the provided context, cite
bracket numbers"), and emits reliable JSON for flashcards. Size is hardware-tunable —
Qwen3-4B for laptop/CPU, 8B for a mid GPU (chosen default), 14B / 30B-A3B for more headroom.
Llama (Community License, 700M-MAU + AUP) and Gemma ≤3 (custom Gemma license) were excluded
as open-weight-but-not-OSI. Grounding-first alternative if stack-coherence is dropped:
Mistral Small 3.2 (Apache 2.0, 24B, tuned to refuse over hallucinate).

Implications and required config work:

- Set `EMBEDDING_DIMENSIONS=1024` (Qwen3-Embedding-0.6B native), down from the current 1536
  (OpenAI `text-embedding-3-small`). The dimension is baked into the pgvector column at
  migration time, so this must be set **before** `alembic upgrade`.
- **Re-ingest all documents** after the switch — existing 1536-dim vectors are incompatible
  with a 1024-dim column.
- Ollama exposes an OpenAI-compatible API, so the existing `OpenAICompatibleProvider` can
  likely be reused by pointing `OPENAI_BASE_URL` at Ollama (e.g. `http://localhost:11434/v1`)
  and setting `EMBEDDING_MODEL`/`CHAT_MODEL`. **Guard the `dimensions` param**:
  `providers.py` sends it (an OpenAI matryoshka feature) and Ollama may reject unknown params
  — make it omittable per provider. Qwen3-Embedding's native 1024 means no truncation is
  needed anyway.
- **Flashcard JSON reliability:** `generate_flashcards` currently relies on `expect_json=True`
  + `json.loads`. Ollama supports structured outputs (`format` = a JSON schema); pass the
  flashcards schema to enforce valid JSON at decode time regardless of model — far more robust
  than prompt-only JSON. Wire this into the provider.
- Update `.env.example`, `docker-compose*.yml`, `README.md`, and `docs/DEPLOYMENT.md` for the
  Ollama + reranker-sidecar topology.

## Phase 1 — pgvector-native retrieval (foundation)

**Why first:** everything downstream (reranking, coverage) depends on getting good
candidates cheaply. The current full-scan approach caps quality and won't scale.

- Replace the Python cosine loop in `retrieve_chunks` with a pgvector ORDER BY distance
  query (`DocumentChunk.embedding.cosine_distance(query_embedding)`), fetching a
  candidate pool (e.g. top 30–50) at the DB layer.
- Convert stored distance to a similarity score for `Citation.score` so the API contract
  is unchanged.
- **Use the index that already exists — and reconsider its type.** Migration `0001`
  already creates an ivfflat cosine index (`ix_document_chunks_embedding`,
  `vector_cosine_ops`, `lists=100`), but nothing queries through it today because ranking
  happens in Python. Two fixes land together:
  - *ivfflat → hnsw:* for a study-app corpus, hnsw gives better recall/latency and is the
    modern pgvector default; ivfflat needs the data present before build (its `lists`
    clusters train on real vectors) and, at `lists=100` on a tiny library, actively hurts
    recall. Migrate the index to hnsw (`vector_cosine_ops`), or keep ivfflat but tune
    `lists` to row count.
  - *Small-corpus guard:* below a threshold (a few hundred chunks) skip the ANN index and
    do exact search — approximate indexes only pay off at scale and degrade recall when tiny.
- Keep a SQLite-safe fallback path so the existing in-memory test suite still runs
  (tests use `sqlite+pysqlite`, which has no pgvector operators).

**Acceptance:** identical top-k on a fixture corpus vs. the old path, but issued as one
indexed SQL query. New test: retrieval returns results without loading all chunks.

## Phase 2 — reranking

**Model + serving decision (fully OSS, local):** rerank the Phase 1 candidate pool with
**`BAAI/bge-reranker-v2-m3`** (Apache 2.0, 0.6B cross-encoder, multilingual, 512-token
context — ample for query/chunk pairs, CPU-friendly). Serve it from a **dedicated sidecar**,
not Ollama: either **llama.cpp `llama-server --reranking`** (MIT, exposes OpenAI-style
`POST /v1/rerank`) or **Infinity** (MIT, `michaelfeil/infinity`). Keep Ollama for chat and
embeddings.

Rationale: Ollama has no native rerank endpoint ([ollama#7219](https://github.com/ollama/ollama/pull/7219)
unmerged >6 months), and classic cross-encoders need `pooling=rank` which Ollama can't do.
The in-Ollama alternative (Qwen3-Reranker via logit-parsing adapter) is hacky and has known
GGUF scoring bugs, so it's rejected here. All picks are Apache/MIT — no non-commercial
weights (jina-reranker's CC-BY-NC-4.0 is excluded).

- Add a `rerank` client that calls the sidecar's `/v1/rerank` (query + candidate texts →
  scored order). Behind a `RERANK_ENABLED` flag; fall back to Phase 1 vector order when
  disabled or the sidecar is unreachable (log the fallback — no silent degradation).
- New `config.py` settings: `rerank_enabled`, `rerank_base_url`, `rerank_model`,
  `retrieval_candidate_k` (pool from Phase 1) and `retrieval_top_k` (final after rerank).
- Add the reranker service to `docker-compose.yml` / `docker-compose.prod.yml` and document
  it in `README.md` + `docs/DEPLOYMENT.md`.

**Acceptance:** reranking reorders a fixture where a lexical-but-irrelevant chunk outranks
the answer-bearing chunk (measured by the Phase 4 eval harness); with the sidecar down, Q&A
still answers via vector-order fallback.

## Phase 3 — context verification + citation coverage

- After generation, verify each answer sentence/claim maps to at least one retrieved
  chunk; compute a **citation coverage score** (fraction of claims grounded).
- Replace the hardcoded `confidence_notes` with real signals: coverage score,
  count of sources actually referenced, and a low-coverage warning.
- Surface coverage on `AskResponse` (additive field) and render it in the frontend
  answer panel (the `.impeccable.md` principle: "make AI output inspectable").

**Acceptance:** an answer that cites nothing scores 0 coverage and shows a warning; an
answer fully grounded scores ~1.

## Phase 4 — evals (retrieval + generation quality)

Two layers, deliberately split by cost and determinism. Both share one **golden dataset**:
a small curated fixture (~10–30 questions over a handful of committed docs, each labelled
with expected source chunk/doc ids and a reference answer) under `backend/tests/eval/`.
This golden set is the foundation — build it first.

### Layer A — deterministic retrieval evals (no LLM judge)

Hand-rolled metrics over the golden set; fast, reproducible, run in normal CI with **no
model and no new heavy deps**.

- **recall@k, MRR, nDCG** of `retrieve_chunks` against expected chunk ids (measures Phase 1
  retrieval + Phase 2 rerank; this is the harness Phase 2's acceptance test refers to).
- **Citation integrity** (deterministic): every answer cites ≥1 source, and every cited
  `chunk_id` actually exists and belongs to a selected document.
- Gate CI on thresholds (e.g. recall@8 ≥ 0.9 on the golden set); a rerank regression fails
  the build.

### Layer B — LLM-as-judge generation evals (opt-in)

Faithfulness / groundedness, answer relevancy, **citation accuracy** (do the cited chunks
actually support each claim?), and hallucination. These need a judge model and are slower +
non-deterministic, so mark them `@pytest.mark.eval` and keep them out of the default run.

- **Framework: DeepEval** (Apache 2.0). It's "pytest for LLMs" — fits the existing pytest
  suite, ships Faithfulness / Contextual Precision·Recall·Relevancy / Hallucination, and
  **G-Eval** for a custom natural-language "citation accuracy" metric StudyGraph needs.
  Judge runs on a **local Ollama** model (`deepeval set-ollama <model>` or a
  `DeepEvalBaseLLM` subclass) — stays fully OSS-local.
- **Judge model caveat:** LLM-judge quality tracks judge strength, and `qwen3:8b` is a weak
  judge. Use a **larger local model as the judge** (configurable, separate from the app's
  chat model — e.g. a 20B–32B class model the host already has), and treat Layer B scores as
  directional, not precise. Keep the judge model in eval config, not app config.
- **Ragas (Apache 2.0) — optional, deferred.** Deepest RAG-specific metric set and nice for
  dataset-level dashboards/trend tracking, but it's **built on LangChain** and would deepen
  that coupling (see below). Add it only if/when dataset-level metric tracking is a real
  need; DeepEval covers the CI-gating case with a lighter footprint.

**Acceptance:** `pytest` (default) runs Layer A and fails on retrieval/citation regressions;
`pytest -m eval` runs Layer B and reports faithfulness / citation-accuracy scores.

### Framework decisions: LangChain / LangGraph

- **LangGraph — not now.** StudyGraph's pipeline is linear (retrieve → rerank → generate);
  LangGraph earns its keep only for *agentic* loops (multi-hop, query planning, self-RAG,
  critique-and-retry). Adding it today is complexity with no payoff. Revisit only if a later
  milestone introduces genuine multi-step study workflows.
- **LangChain — don't add more; trim what's there.** It's already a dependency, used only in
  `chunking.py` (`SemanticChunker` + `RecursiveCharacterTextSplitter`). Two cleanups:
  (a) `langchain-openai` is declared in `pyproject.toml` but imported nowhere — dead since
  the OSS migration; remove it. (b) `langchain-experimental` (SemanticChunker) is on a
  sunset track (deprecation warnings in the test run) — consider replacing semantic chunking
  with a lighter splitter or pinning it. Choosing **DeepEval over Ragas** keeps evals from
  re-entrenching LangChain.

## Phase 5 — observability

- Structured timing + counts around ingestion, retrieval, each provider call, and answer
  generation (extend `app/core/logging.py`; consider a lightweight timing context
  manager).
- Log candidate pool size, rerank deltas, coverage score, and provider latency/token
  usage per request.

**Acceptance:** one Q&A request emits a structured trace covering retrieval → rerank →
generation → coverage with timings.

## Phase 6 — retry controls + chunk inspection

- Retry endpoints/UI for failed ingestion jobs and failed generations (the ingestion job
  model in `0002_document_ingestion_jobs` already tracks status).
- Better document/chunk inspection: expose chunk boundaries and retrieved-chunk
  highlighting in the frontend (`app/api/documents.py` already has `/{id}/chunks`).

**Acceptance:** a failed ingestion job can be retried from the UI without re-upload;
retrieved chunks are inspectable per answer.

## Suggested order

1 → 4 → 2 → 3 → 5 → 6. Land Phase 1 and the eval harness (Phase 4) together so every
later change is measured against real numbers before/after.
